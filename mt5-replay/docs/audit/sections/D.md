## D. POTENTIAL TECHNICAL RISKS

This section carries the part of the audit that source alone could not close. It has three parts and each states its count at the top:

- **Potential risks (D.1) — 30.** Findings that survived all three adversarial refuters but whose harmful outcome turns on MetaTrader, broker or locale behaviour that cannot be read out of the tree. Each carries the exact real-terminal test that would confirm or clear it.
- **Refuted (D.2) — 21.** Candidates that were put to the same three refuters and **did not survive**. They are printed with the reason, because an audit that refutes nothing has not been checked.
- **Coverage statement (D.3) — areas checked with no defect found.** Explicit "checked, clean" lines, so that silence in sections C and D.1 can be distinguished from absence of reading.

Two standing facts frame everything below. **[CONFIRMED FROM CODE]** The author has never run this codebase on a real MetaTrader terminal — MT5 cannot be installed in the build environment — so *no* finding in this document has been observed at runtime; CONFIRMED means confirmed from source by adversarial review. **[CONFIRMED FROM CODE]** A grep for `OrderSend`, `OrderSendAsync`, `CTrade` and `PositionClose` across `MQL5/` returns 7 hits and every one of them is a comment asserting the absence (`SSReplayStandalone.mq5:305`, `SSR_TradingEngine.mqh:6`, `SSR_TradeTypes.mqh:5`, `SSR_IStrategy.mqh:8,18`, `SSR_Publisher.mqh:19`, `SSR_ReplayPort.mqh:341`). #### D.1.1 `data-2` — HIGH — `MQL5/Include/SSReplay/Data/SSR_BarWindow.mqh:218`
*One invalid-OHLC or non-positive M1 bar voids the entire read window, and the provider reports that as zero bars with success.*

**The claim.** **[CONFIRMED FROM CODE]** `SSRDataReport::IsUsable()` is `total>0 && invalid_ohlc==0 && nonpositive==0` (`Data/SSR_DataValidator.mqh:54-57`), and `ValidateBars` sets those flags per bar over the entire loaded array (`:247-250`). `SanitizeBars` (`:265-282`) only enforces strictly increasing open times and never inspects prices — so it cannot repair what the report refuses. One bar with `high < low`, `high < max(open,close)`, `low > min(open,close)` or any price `<= 0` therefore makes `CSSRBarWindow::Ensure` call `Fail(SSR_ERR_NO_DATA)` + `Invalidate()` and discard every good bar in a span of `max(request, m_window_bars)` = 5,000..60,000 minutes (`Data/SSR_HistoryCatalog.mqh:209-215`). `CSSRMt5BarProvider::ReadBars` then maps exactly that error to `Succeed(); return 0;` (`Data/SSR_Mt5Providers.mqh:265-275`), and `EmitWindow` does `if(nb <= 0) { m_cursor.Advance(hi,0,0); return 0; }` (`Core/SSR_ReplayController.mqh:389-394`): the clock advances, no candle appears, no error is set and no log line is written. `SeedWarmup` takes the same zero and skips `SeedBars` (`:885-898`), so the session can also start with no context candles. **[CONFIRMED FROM CODE]** Two consequences the original write-up missed, added by the verifiers: the report is computed *before* sanitisation, so even a bad bar that sanitisation would have dropped as a duplicate still voids the window; and because `Ensure()` calls `Invalidate()`, `Covers()` fails on every subsequent pump, so the full 5,000–60,000-bar `CopyRates` plus validation is re-run **on every pump** for as long as the bad bar sits inside the forward window — a hard performance stall on top of the blank chart (cross-reference section E).

**Why it could not be settled from source.** Every link in the chain is provable; the *trigger* is not. Whether MT5-served M1 history for a given broker and instrument actually contains a bar with `high < low` or a zero/negative price is broker data, not code. The file's own header says "broker history is not guaranteed clean", and `SSR_T2_DataEngine.mq5:136-143` asserts only that the report *flags* bad OHLC — no test covers what the window and the engine then do. **[INFERENCE]** On a normally-behaved FX feed this may never fire; on a thin CFD, an index with a holiday zero-print, or imported history it is the most damaging risk in this list, because the failure is completely silent.

**Exact real-terminal test.**
1. *Does the trigger exist on this broker?* Run a one-off script: for each symbol in Market Watch, `CopyRates(sym, PERIOD_M1, 0, 200000, r)` and count bars where `r[i].high < r[i].low || r[i].high < MathMax(r[i].open,r[i].close) || r[i].low > MathMin(r[i].open,r[i].close) || r[i].open<=0 || r[i].high<=0 || r[i].low<=0 || r[i].close<=0`. Print symbol, count and the first offending bar time. **Any non-zero count confirms the trigger.**
2. *Does the failure behave as described?* Create a custom symbol, `CustomRatesUpdate` 10,000 clean M1 bars, then replace one bar in the middle with `high = low - 10*point` via a second `CustomRatesUpdate`. Run a session whose window spans that bar. Observe: (a) candles stop appearing while the clock in the panel keeps moving; (b) the Experts log prints nothing at the moment it stops; (c) terminal CPU rises (the per-pump reload). All three together confirm the finding end to end.
3. *Clear it* only if step 1 returns zero across every instrument the product supports **and** step 2's synthetic bar produces a visible error message rather than silence.

#### D.1.2 `host-expert-12` — MEDIUM — `MQL5/Experts/SSReplay/SSReplayStandalone.mq5:681`
*The history download gives up after ~1.8 s of no completed bars.*

**The claim.** **[CONFIRMED FROM CODE]** The loop asks with `CopyRates`, `Sleep(300)` (`:671`), and counts a stall whenever `Bars()` has not grown; `if(++stalls >= 6)` (`:681`) abandons the request, with `stalls` reset only on growth (`:690`). Six consecutive dead passes is roughly 1.8 s of sleeping plus the `CopyRates` calls, against a stated 60-second budget at `:653` and a request for `InpHistoryBars` = 60,000 M1 bars. The message printed blames the broker ("Usually that is all the broker serves for this symbol"), and the user then meets the SHORT ON HISTORY cascade at `:1109-1145` with a window far smaller than they asked for. `ResetLastError()` *is* called at `:668`, but the `CopyRates` return value is discarded, `GetLastError()` is never read and `SeriesInfoInteger(..., SERIES_SYNCHRONIZED, ...)` is never tested — so nothing distinguishes "no download is running" from "a download is running and has not committed a bar yet". The comment says "Two dead passes" while the code allows six, so the intended budget was never settled.

**Why it could not be settled from source.** Whether MT5 commits a first block of a 60,000-bar asynchronous request within 1.8 s, and how quickly `Bars()` reflects it, is terminal, broker and link behaviour. MQL5's documented idiom for an unsynchronised series is to retry for several seconds, which makes the risk plausible — but plausible is not provable here.

**Exact real-terminal test.** On a machine with no local history for the target symbol (delete the symbol's `bases\<server>\history\<symbol>` folder with the terminal closed, or use a symbol never opened), set `InpHistoryBars=60000` and start a session. Record: the wall time between the first and last `[host] history:` log lines; the bar count reported at abandonment; then, without changing anything, restart the session and record the bar count again. **Confirms** if the second run reports materially more bars than the first (the download was in flight and was abandoned). **Clears** if both runs report the same count and `Bars()` stops growing while the terminal's Symbols dialog shows the full history already local. Repeat on a throttled connection (100 kbit/s) — that is the configuration the risk is really about.

#### D.1.3 `chart-1` — MEDIUM — `MQL5/Include/SSReplay/Chart/SSR_ChartManager.mqh:452`
*`DetectScroll` cannot tell bar arrival from a drag at high speed.*

**The claim.** **[CONFIRMED FROM CODE]** `votes_needed` collapses to 1 as soon as `m_last_bar_time > 0` (`:452`, set in `Redraw`, `:548`), so a single sample can detach. The threshold is `SSR_SCROLL_DETACH_BARS` = 3 (`Chart/SSR_ChartTypes.mqh:25`). `Sync()` runs at `SSReplayStandalone.mq5:2820` and `Redraw()` at `:2830`, every fifth pump, so the offset measured is everything that accumulated since the previous snap. A detach latches `user_detached = true` and switches `CHART_AUTOSCROLL` off (`:460-463`), and `Redraw`'s snap is gated on `!user_detached` (`:574`), so there is no automatic recovery — only the F key (`FollowAll`) or a timeframe change. Nothing compares the drift against how many bars actually arrived, although `m_last_bar_time` is available.

**Why it could not be settled from source, and one correction.** **[CONFIRMED FROM CODE]** The original "tens of M1 bars per 200 ms" arithmetic is wrong: `CSSRReplayClock::Advance` multiplies wall delta by `speed_x100/100` with no special case (`Core/SSR_ReplayClock.mqh:94-111`), so MAX is literally 1000x, and at the default `InpPumpMs=40` a five-pump interval advances ~200 s ≈ 3.3 M1 bars — just under the `off > 3` test. The false positive therefore needs the starvation ceiling to be hit (delta clamped to `4*InpPumpMs`, `SSReplayStandalone.mq5:2754`), which can push one interval to ~13 M1 bars, *and* it needs `CHART_SHIFT` (`:315`) not to be absorbing the first bars of drift into `ViewOffset`'s negative clamp (see `chart-8`). On M5 and above the arithmetic never reaches the threshold. The decisive unknown is whether MetaTrader's own autoscroll fails to keep the newest bar in view on an EA-written custom symbol — the premise the whole file is built on (`:509-521`) and which nothing in the tree measures.

**Exact real-terminal test.** One-chart mode, M1, speed MAX, hands off the mouse and trackpad, run 15 minutes under deliberate load (open five other charts and a heavy indicator so the timer starves). Instrument the build with one temporary `Print` in `DetectScroll` recording `first_visible`, `visible_bars`, the computed offset and the vote count on every `Sync`. **Confirms** if a detach is logged with no mouse input — the log will show an offset > 3 in one pass. **Clears** if the offset never exceeds 3 across the whole run at MAX speed with starvation. Repeat once on M5 to verify the "never reaches threshold above M1" correction.

#### D.1.4 `mt5-symbol-2` — MEDIUM — `MQL5/Include/SSReplay/Mt5/SSR_CustomSymbolManager.mqh:476`
*`Adopt()` does not force `SYMBOL_CHART_MODE_BID`.*

**The claim.** **[CONFIRMED FROM CODE]** `Create()` forces `SYMBOL_CHART_MODE` to BID at `:383` and reads it back into `m_chart_mode_ok` at `:387-395`, behind a 28-line banner calling this "the defect that outlived every other". `Adopt()`'s re-apply block (`:476-481`) sets `SPREAD_FLOAT`, `TRADE_MODE`, `Apply247Sessions` and `CloneMoneyProperties` and never touches `SYMBOL_CHART_MODE`, although its own comment says a symbol from an older run "may have been created before one of them existed". `git log -S` confirms the BID force arrived only in commit 9235491 (v120). Both `Adopt` doors are live: seed-cache reuse (`Mt5/SSR_CustomSymbolSink.mqh:168`) and the one-window `adopt_existing` handover (`:178`), which is reachable when the EA restarts on a leftover replay chart (`SSReplayStandalone.mq5:2197-2199`). `m_chart_mode_ok` also keeps its constructor value `false` after any adoption — presently inert, since `ChartModeOk()` has no caller anywhere in the tree.

**Why it could not be settled from source.** The harm needs a **pre-v120 LAST-mode replay symbol to still exist in the user's terminal**, which requires that `CustomSymbolSetInteger` properties persist in the symbols base across restarts, and it needs the "ticks accepted, no candle built" behaviour to be real. Both are terminal behaviours; within this build every `Create()`-made symbol is already BID.

**Exact real-terminal test.** (a) `CustomSymbolCreate("ZZTEST.SSR9", "SSR", "EURUSD")`, `CustomSymbolSetInteger("ZZTEST.SSR9", SYMBOL_CHART_MODE, SYMBOL_CHART_MODE_LAST)`, close the terminal, reopen, read `SymbolInfoInteger("ZZTEST.SSR9", SYMBOL_CHART_MODE)`. **Persistence confirmed** if it still reads LAST. (b) With it still in LAST mode, `CustomTicksAdd` a run of BID/ASK ticks and `CopyRates` the M1 series: **confirmed** if the bar count stays 0 while ticks are accepted. (c) Then start the EA on a chart of that symbol so the `Adopt` path runs and verify the mode is still LAST afterwards. Any of the three coming back the other way clears the corresponding half.

#### D.1.5 `mt5-symbol-4` — MEDIUM — `MQL5/Include/SSReplay/Mt5/SSR_CustomSymbolManager.mqh:514`
*`CloseCharts()` may close the chart the EA itself runs on.*

**The claim.** **[CONFIRMED FROM CODE]** `CloseCharts()` (`:505-522`) walks `ChartFirst`/`ChartNext` and closes on a bare `ChartSymbol(id) == m_symbol` match with **no `id == ChartID()` exclusion**. It runs from `Destroy()` (`:549`), which runs from the sink's `Release()` (`Mt5/SSR_CustomSymbolSink.mqh:384-390`), from the sink destructor (`:72-74`) and from `Create()` (`:318`). The ownership gate `m_own_symbol` does not help: `SetOwnsSymbol` is never called by the Expert (only by `SSR_T6_History.mq5`), so it stays `true`. In one-window teardown the EA does `ChartSetSymbolPeriod(ChartID(), g_origin, _Period)` at `SSReplayStandalone.mq5:2192`, whose own comment at `:2186` records the switch as **asynchronous**, and then calls `g_ctrl.Release()` at `:2202-2204`. If `ChartSymbol(ChartID())` still reports the replay symbol at that instant, the loop closes the user's own window instead of returning it to the origin.

**Why it could not be settled from source.** Two terminal behaviours decide it: whether `ChartSymbol()` reflects a queued `ChartSetSymbolPeriod` synchronously, and whether `ChartClose` on one's own chart is honoured from inside `OnDeinit`. Neither is documented in a way that settles the race.

**Exact real-terminal test.** One-window mode, second pass (the EA's chart is showing the replay symbol). Remove the EA from the chart (right-click → Expert Advisors → Remove), then check whether the window still exists and what symbol it shows. Repeat three times, and repeat once by closing the terminal outright with the profile set to save. **Confirms** if the window disappears in any trial. **Clears** if the chart always survives and returns to the origin symbol. **[RECOMMENDATION]** Regardless of the result, add `if(id == ChartID()) { id = ChartNext(id); continue; }` to the loop — the fix costs one line and removes the need for the test.

#### D.1.6 `mt5-symbol-5` — MEDIUM — `MQL5/Include/SSReplay/Mt5/SSR_CustomSymbolSink.mqh:73`
*The sink destructor tears the symbol down on any object death; the EA never transfers ownership for the `REASON_CHARTCHANGE` handover.*

**The claim.** **[CONFIRMED FROM CODE]** `g_sink` is a global object (`SSReplayStandalone.mq5:190`), `m_own_symbol` is initialised `true` (`:65`), and `SetOwnsSymbol` is called only by `SSR_T6_History.mq5:238/256/273` — never by the host. `OnDeinit` deliberately withholds `Release()` for every reason except REMOVE/PROGRAM/CLOSE (`:2121-2124`, `:2152-2204`), because pass 2 of the one-window handover must adopt the symbol. So nothing clears ownership before the unload. If MT5 destructs EA globals on a `REASON_CHARTCHANGE` unload — which the EA's own comments at `:1866` ("globals are re-initialised") and `:2122` assert — then `~CSSRCustomSymbolSink` calls `m_mgr.Destroy()`, which runs `CloseCharts()` over every chart showing the replay symbol **including the chart being handed over** and then `CustomSymbolDelete`.

**Why it could not be settled from source.** Whether MQL5 executes global-object destructors on `REASON_CHARTCHANGE`, and if so whether `ChartSymbol()` at that instant already reports the replay symbol, is runtime semantics no file in the tree settles. Both branches are consistent with the source, and there is no guard that makes the handover correct under both. **[INFERENCE]** The delete itself would most likely fail (MetaTrader refuses to delete a symbol a chart is open on — the premise `SetAdoptExisting` exists for), so the **chart closure, not the symbol deletion, is the hazard**; the author reports pass 2 adopting successfully, which suggests the destructor does not run on that terminal.

**Exact real-terminal test.** Add one temporary `Print("~sink")` as the first statement of `~CSSRCustomSymbolSink`. Start in one-window mode and let pass 1 hand over. Read the Experts log. **Confirms the trigger** if `~sink` appears between the two initialisations; then check whether the chart survived and whether `SymbolInfoInteger(rsym, SYMBOL_EXIST)` is still 1. **Clears** if `~sink` never prints on `REASON_CHARTCHANGE` (globals survive the reload). **[RECOMMENDATION]** Either way, have the EA call `g_sink.SetOwnsSymbol(false)` before returning from the CHARTCHANGE branch and re-arm it in pass 2 — that makes the handover correct under both branches without needing the answer.

#### D.1.7 `mt5-symbol-6` — MEDIUM — `MQL5/Include/SSReplay/Mt5/SSR_CustomSymbolSink.mqh:205`
*`Prepare()` discards the result of the truncate that removes the previous session's replay data.*

**The claim.** **[CONFIRMED FROM CODE]** The reuse branch is `if(m_warmup_to_msc > 0) m_mgr.Truncate(m_warmup_to_msc + 1);` with the `long` return discarded, and execution falls through to `m_prepared = true; return true;` (`:215-216`). `CSSRCustomSymbolManager::Truncate` (`:713-744`) has two `-1` paths — `CustomRatesDelete < 0` and `CustomTicksDelete < 0` — each of which also sets `SSR_ERR_SINK_FAILED` on the manager, state `Prepare` never reads. `TruncateFrom` (`Sink:348-353`) *does* honour the `-1`, which proves the author knew the contract. `ClearAll` (`Manager:747-756`) is worse: it ignores both delete results, calls `Succeed()` — clearing any prior error — and unconditionally returns `true`; `Prepare` ignores it at `:186` and `:198`, so the adopt-existing and fresh paths have the same blind spot. If a delete fails, the previous session's candles remain on the chart **as this session's future** — the "hidden-but-present future" the file header at `:18-21` names as the product's defining failure.

**Why it could not be settled from source.** Whether `CustomRatesDelete`/`CustomTicksDelete` can fail on a selected custom symbol that `Adopt()` has just verified is terminal behaviour. The unchecked result is proven; the harmful outcome is not.

**Exact real-terminal test.** Run session A over a window, let it produce bars, stop. Start session B on the **same** symbol and slot with a *later* start instant so the cache-hit path is taken. Before the first pump (pause on start, `InpPauseSession=true`), run `CopyRates(rsym, PERIOD_M1, start_time, end_time, r)` from a second script and count bars after the replay start instant. **Confirms** if the count is non-zero — the truncate did not remove them and nothing said so. Second variant: hold an open chart on the replay symbol in a different timeframe while B starts, which is the state most likely to make a delete refuse. **Clears** if the count is zero in both variants across ten runs. **[RECOMMENDATION]** Independent of the result, check the return values and fail `Prepare()` — a silent future is the one failure this product cannot ship.

#### D.1.8 `ui-panel-11` — MEDIUM — `MQL5/Include/SSReplay/Ui/SSR_Panel.mqh:1299`
*The Setup tag box is hidden, re-shown and fully rewritten on every repaint while the user is typing in it.*

**The claim.** **[CONFIRMED FROM CODE]** `HideSheets()` calls `ReadTag()` then `m_w.Hide("tagbox", true)` (`:1298-1299`) as the **first statement of `DrawSheet`** (`:1270`), i.e. on every frame and every tab; `SheetTrade` then re-issues `m_w.Edit("tagbox", ...)` (`:1375`) and `m_w.Hide("tagbox", false)` (`:1376`). `CSSRWidgets::Hide` writes `OBJPROP_TIMEFRAMES` on both calls (`Ui/SSR_Widgets.mqh:619-621`), and `CSSRWidgets::Edit` has **no cache at all** — it writes XDISTANCE, YDISTANCE, XSIZE, YSIZE, BGCOLOR, COLOR, BORDER_COLOR, FONTSIZE and READONLY unconditionally, `m_writes += 9` (`:305-319`). At 10 renders per second that is 110 property writes per second on the one control whose contents belong to the user. The file's own comment at `:1286-1297` records that destroying and rebuilding this object "does not merely lose the text — it makes the box impossible to type in at all".

**Why it could not be settled from source, with two mitigations.** **[CONFIRMED FROM CODE]** The text is safe: `Edit` is called with `set_text=false` on an existing object, so `OBJPROP_TEXT` is not rewritten (`Ui/SSR_Widgets.mqh:319-325`). No flicker is expected either: both `TIMEFRAMES` writes happen inside one `Render()` before its single `ChartRedraw` (`:829`), so the net painted state is unchanged. The residual question is narrow and purely runtime: **does MetaTrader act on a visibility write to a focused `OBJ_EDIT` immediately** — dropping keyboard focus or a queued keystroke — rather than at redraw?

**Exact real-terminal test.** Open the Trade tab, click into the tag box, and type a known 40-character string at a steady pace (or paste it, then type ten more characters) while the replay is **running** at 1x so `Render()` is firing ten times a second. Compare what is in the box with what was typed, and note whether the caret is ever lost mid-word. Repeat with the replay paused (fewer repaints) as the control. **Confirms** if characters are lost or focus drops only while running. **Clears** if 40/40 characters land in both conditions across five trials. **[RECOMMENDATION]** The cheap structural fix is to exempt `"tagbox"` from `HideSheets()` when the Trade tab is the active tab, so the hide/show pair never runs on a visible, focused box.
