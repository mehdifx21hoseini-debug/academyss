## S. TRADE JOURNAL

*Scope: `CSSRJournal` (`SSR_Journal.mqh`, 1254 lines) and `CSSRShotBook` (`SSR_ShotBook.mqh`,
311 lines), the disk layout under `MQL5/Files/SSReplay/journal`, the CSV contract that
`CSSRStatsEngine`, `CSSRClassReport` and every spreadsheet downstream of it read, and the one
panel surface that can open a single trade. Build v125. This section stays inside the architecture
M chose: the journal is **not a rail destination in v1** (M.3.2, N.9), and nothing here asks it to
be. What it does is build the record first — on disk, where the record can be complete — and then
specify the destination exactly as N.9 promised, so that when the accessor lands the page is a
`ListRO` and a detail screen and nothing else.*

---

### S.0 The position, in one page

There are two classes, and between them they already do the hard half of the job. What is missing
is not a feature. It is **the record**.

[CONFIRMED FROM CODE] `CSSRJournal::Row` (`SSR_Journal.mqh:69-90`) writes eighteen columns:

```
ticket,type,tag,volume,open_time,open_price,close_time,close_price,
reason,profit,commission,swap,r,duration,mae,mfe,resolution,note
```

[CONFIRMED FROM CODE] `SSRVirtualPosition` (`SSR_TradeTypes.mqh:178-291`) carries, per trade, and
**never writes to that file**: `sl`, `tp`, `risk_at_entry`, `spread_at_entry`, `spread_at_exit`,
`trail_points`, `request_price`, `request_msc`, `legs[]`. The stop and the target — the two numbers
a trainee is reviewed on — are on the struct, are persisted into the session file
(`SSR_TradingEngine.mqh:1080-1081`, fields 10 and 11), and do not appear in the journal.

[CONFIRMED FROM CODE] `note` is worse than missing: it is packed at field 27 on save
(`SSR_TradingEngine.mqh:1097`), restored at field 27 (`:1210`), printed as the CSV's last column
(`SSR_Journal.mqh:89`) — and **nothing anywhere assigns it**. A grep over `MQL5/` for a writer
returns the pack line, the unpack line and the print. The per-trade review already has a persistence
path, a schema slot and an export column. It has never had a way in.

So the shape of this section is:

1. **S.2-S.3 — finish the record.** Six fields onto the position, one accounting rule published in
   the file, and the CSV's eighteen columns become thirty-one. This ships without touching the panel.
2. **S.4-S.6 — give it a place to live.** One folder per run, a versioned schema, and a separate
   append-only `review.csv` so that writing a note can never truncate the export
   (`ui-port-session-2`, CONFIRMED MEDIUM, is the lesson and it applies here verbatim).
3. **S.7 — three pictures, not two**, and the panel out of them (`trading-analytics-15`, **POTENTIAL_RISK, IMPROVEMENT** — what a screenshot contains is a rendering fact this audit has no evidence for).
4. **S.8-S.9 — the destination**, built on the indexed accessor N.9 named as its one prerequisite —
   which, once built, also repairs three CONFIRMED statistics findings that are all the same defect:
   *closed trades are walked in slot order, not close order.*

**The one number that must change first.** [CONFIRMED FROM CODE] `trading-analytics-4` (CONFIRMED,
MEDIUM): the CSV's `profit` column is raw `p.profit` (`SSR_Journal.mqh:82`) while the HTML statement
prints `net = p.profit + p.swap - p.commission` (`:394`) and `ComputeFor` decides wins from that same
net (`SSR_Statistics.mqh:431`). Three documents generated by one class, from one account, disagree
about whether a trade won. Everything else in this section is worth less than fixing that.

#### S.2.1 Slippage: recorded, never derived

[RECOMMENDATION] Two fields on `SSRVirtualPosition`, beside `spread_at_entry`/`spread_at_exit` and
for the same stated reason (`SSR_TradeTypes.mqh:212-220`: *"Recorded rather than derived, because by
the time the statement is written the minute is gone"*):

```
   double   slip_entry_points;   // adverse, points, at the fill
   double   slip_exit_points;    // adverse, points, at the final exit
```

Two write sites, both already computing the number:

* `CSSRTradingEngine::Open`, `SSR_TradingEngine.mqh:743` — `open_price = FillPrice(is_long, true)`.
  `FillPrice` (`:120-126`) adds `slip = m_exec.slippage_points * m_point`. Entry slippage is
  therefore the model constant, and recording it is what makes an **old** or **restored** file
  honest about the assumption it ran under rather than about the one currently configured.
* `CSSRTradingEngine::StopFill`, `:492-510` — and this one is genuinely new information. The
  function takes *"the worse of the level and the price that touched it"* and then applies slip, so
  a stop that gapped through fills far past its level. [CONFIRMED FROM CODE] the realised distance
  `|fill − p.sl|` is computed inside this function and discarded. It is the difference between *"my
  stop was hit"* and *"my stop was hit and cost me 2.4 R"*, and it is the single most useful number
  in this section that the product currently throws away.

[RECOMMENDATION] the same two write sites also record `balance_at_entry` (the engine holds
`m_balance`, `:956`, and debits commission one line later at `:748`), which is the denominator
`risk_pct` needs. Without it, *"you risked 2.6 % on that one"* cannot be said about a trade
reviewed after the balance moved.

[CONFIRMED FROM CODE] All three fields are appended to the session-file record under the rule the
file already states at `SSR_TradingEngine.mqh:1070-1075`:

```
                //--- APPENDED, never inserted: a reader that predates
                //--- these two fields stops at `note` and is unharmed,
                //--- and a file that predates them restores as zero
                "spread_at_entry|spread_at_exit");
```

That comment is the precedent S.5's CSV rule is copied from. It is already the product's law for one
serialised format; the journal simply has not been held to it.

#### S.2.2 Session: a declared table, not a guess

[CONFIRMED FROM CODE] The only clock the journal has is `open_msc` interpreted by
`TimeToStruct((datetime)(p.open_msc / 1000), dt)` (`SSR_Statistics.mqh:246`) — i.e. **server hours,
with no offset known to this program**. Nothing in the tree records a broker UTC offset.

[RECOMMENDATION] Therefore the session label may not be inferred. It is declared, in server hours,
and the declaration travels in the file:

```
   # session_table,Asia 00-07;London 07-13;NewYork 13-21;Late 21-24
   # session_basis,server
```

and `session` becomes a column computed by one function, `SSRSessionName(hour)`, fed from the same
`dt.hour` the hour bars already use. A reader that disagrees with the boundaries can recompute from
`open_time`; a reader who never sees the table cannot check the label at all. [POTENTIAL_RISK] the
boundaries are a convention, not a fact about any broker; the header line is what keeps that honest.

#### S.2.3 Mistake flags: one owner, one pass, no second formula

M.4.1's rule for `DailyRoomAfter()` applies unchanged here — *the arithmetic must not happen in the
reader*. [CONFIRMED FROM CODE] `CSSRStatsEngine::ComputeFor` already evaluates every one of these
predicates per trade and then throws the per-trade answer away, keeping only the count:

| Flag | Predicate, already written | Site |
|---|---|---|
| `NOSTOP` | `!p.HasR()` → `out.trades_without_stop++` | `SSR_Statistics.mqh:458-459` |
| `AMBIG` | `p.ambiguous` → `out.ambiguous_trades++` | `:461-462` |
| `REVENGE` | `prev_was_loss && (p.open_msc − prev_close) <= SSR_REVENGE_WINDOW_MSC` | `:497-500` |
| `WIDESPRD` | `p.spread_at_entry >= 2 × out.avg_spread_points` → `out.wide_spread_trades++` | `:581` (second pass, after the average exists) |
| `OVERSIZE` | `risk_at_entry` against the session mean; `risk_sum`/`risk_sq_sum`/`risk_samples` are accumulated at `:479-485` and reduced to one aggregate `risk_spread_pct` | derived at the same site |
| `NOTARGET` | `p.tp == 0` — **not currently counted anywhere** | new, one comparison in the same loop |

[RECOMMENDATION] `ENUM_SSR_TRADE_FLAG` as a bitfield, and one new method on `CSSRStatsEngine`:

```
   //--- the per-trade answers the aggregate counters were already
   //--- computing. Same pass, same predicates, same file: a second
   //--- definition of "revenge" in the journal is how two numbers in
   //--- one document come to disagree.
   int   FlagsFor(const int index);          // O(1) against a built index
   void  ComputeFlags(int &out[]);           // filled by the pass at :406-511
```

**`WIDESPRD` and `OVERSIZE` are session-relative**, so they are not stable properties of a trade —
they change as the session goes on. That is a real property of the measure, not a defect, and the
CSV is written once at the end, where the session is complete. [RECOMMENDATION] the panel's detail
screen must therefore label them *"wide for this session"*, not *"wide"*.

### S.3 Raw versus net, and the accounting rule the file must publish

#### S.3.1 The defect

[CONFIRMED FROM CODE] `trading-analytics-4` (CONFIRMED, **MEDIUM**). Three readers of one account:

```
SSR_Journal.mqh:82        p.profit, p.commission, p.swap,            <- CSV: raw, three columns
SSR_Journal.mqh:394       double net = p.profit + p.swap - p.commission;   <- HTML: net
SSR_Statistics.mqh:431    double net = p.profit + p.swap - p.commission;   <- wins/losses
SSR_ClassReport.mqh:266   out.won = (pnl > 0.0);        <- from the CSV's `profit` column
```

With `InpCommission = 3` and a 1-lot trade that made +2, the statement counts a loss, the CSV says
`+2`, and the class report — the document a coach ranks a room of students with — marks it won. The
CSV header's `# net_profit` (`SSR_Journal.mqh:201`) no longer equals the sum of the column
underneath it.

[CONFIRMED FROM CODE] The comment at `SSR_Statistics.mqh:415-430` says this was already found and
fixed once: *"Two accounting rules in one file… A statement that contradicts itself is worse than
none — it is a document the user might show someone."* It was fixed for the HTML and for
`ComputeFor`. The CSV and, through it, the class report were not part of that fix.

#### S.3.2 The fix, in the order it must be applied

[RECOMMENDATION] Three changes, and the order matters because `CSSRClassReport` reads the file.

1. **Add `net`, do not repurpose `profit`.** [CONFIRMED FROM CODE] `CSSRClassReport::ReadOne`
   locates its columns **by name** (`SSR_ClassReport.mqh:238-245`: `open_time`, `profit`, `r`), so
   appending a column is safe and renaming one is not. `profit` keeps meaning raw realised P/L
   forever; `net` is added and is the authoritative per-trade result.
2. **Teach the class report to prefer it.** One arm beside the existing three —
   `if(c == "net") c_net = i;` — and `out.won = (Field(f, c_net >= 0 ? c_net : c_profit) > 0)`.
   A v1 file still parses, still uses `profit`, and still says so, because the schema line (S.5)
   tells the reader which it got.
3. **Publish the rule in the header, so no fourth reader can invent a fifth rule:**

```
   # result_basis,profit+swap-commission
   # r_basis,profit+swap           <- S.3.3; deliberately different, and named
```

[RECOMMENDATION] and one assertion, in `SSR_T10_Statistics.mq5`, that is the only thing that can
keep this fixed: **`# net_profit` equals the sum of the `net` column, to the cent, with commission
and swap both non-zero.** [CONFIRMED FROM CODE] the finding's own evidence says why it survived:
*"With the default commission 0 and swap 0 all three agree, which is why no test catches it."* A
test written at the default values cannot fail.

#### S.3.3 The second accounting split, which is not the same one

[CONFIRMED FROM CODE] `trading-analytics-10` (CONFIRMED, LOW): `RMultiple()` is
`(profit + swap) / risk_at_entry` (`SSR_TradeTypes.mqh:269-270`) — **no commission term** — while
every money measure includes it. On a scalping session `average_r` can be positive while
`expectancy` in money is negative, and the statement prints both side by side.

[RECOMMENDATION] Do not silently change `RMultiple()`. R is a ratio against risk taken, and a reader
comparing an R printed by this build against one printed by the last has no way to know the basis
moved. Instead:

* publish `# r_basis,profit+swap` now, in every file;
* add **one** column, `r_net` = `(profit + swap − commission) / risk_at_entry`, empty on the same
  condition as `r`;
* and let a later build flip `r_basis` to `profit+swap-commission` as a **declared** change, with
  `RMultiple()` as the single owner (`SSR_TradeTypes.mqh:269`) and `SSR_Statistics.mqh:454-457` its
  only caller of consequence.

Two columns, one header line, and the ambiguity is documented rather than argued about.

#### S.3.4 Undefined is empty, and never zero

[CONFIRMED FROM CODE] `trading-analytics-6` (CONFIRMED, LOW). `SSR_Statistics.mqh:526-530` leaves
`profit_factor` at `0.0` when there is no loss, on purpose:

```
      //--- profit factor is undefined without a loss; reporting it as
      //--- infinity or as the gross profit both mislead, so it stays 0
      //--- and the caller reads trades/losses to know why
```

Four printers ignore that contract and format the raw double: the KPI grid (`SSR_Journal.mqh:304`),
the by-setup table (`:359-363`), the CSV header (`:200`) and `Summary()`. A flawless session is
reported as *"Profit factor 0.00"*, which is the worst possible reading of the best possible result,
and the class report ingests the zero (`SSR_ClassReport.mqh:224`).

[RECOMMENDATION] Generalise the rule the `r` column already follows (`SSR_Journal.mqh:83-85`) into
the schema's first law:

> **A measure that is undefined is written as an empty value. Every reader treats an empty value as
> *not known*, never as zero.** Where a reader cannot represent "not known", it must print `-`.

Applied: `# profit_factor,` is written empty when `losses == 0`, and `# losses,%d` is added beside it
so the file states the reason the way the statistics comment says the caller should read it. The KPI
grid and the by-setup table print `-`, which `WriteAllMeasures` (`:1099-1103`) already does correctly
on the same page — the inconsistency is inside one document.

#### S.3.5 The units defect

[CONFIRMED FROM CODE] `trading-analytics-8` (CONFIRMED, LOW): `WriteAllMeasures` prints
`Average MAE`/`Average MFE` with `DoubleToString(st.avg_mae, 2)` (`SSR_Journal.mqh:1142`) while
`mae`/`mfe` are **price distances** (`SSR_TradingEngine.mqh:295-299`), so a 15-pip EURUSD excursion
renders `-0.00`; and the caption compares that price distance with an average win in money.

[RECOMMENDATION] The journal is where this is fixed because it is the only surface that knows the
digits: print excursions in **points** (`/ m_point`, the engine's own unit for `spread_at_entry`),
and add money beside it where a volume exists — `RiskOf(volume, move)` is the existing converter
(`SSR_TradingEngine.mqh:485-489`). The CSV gets `mae_points`/`mfe_points` appended; `mae`/`mfe` keep
their `%.5f` price meaning under the never-repurpose rule.

Four properties, each of which the flat layout cannot have:

1. **A run is copyable.** [CONFIRMED FROM CODE] `RelPath` already returns a path *relative to the

2. **The pictures and the numbers share one key.** No export can reference a run it did not come from.
3. **`SSReplay-session` stops colliding.** The name is derived, not passed; the three callers keep
   their verbs and lose their naming.
4. **A test cannot pollute the trader's journal.** `tests-b-16` closes by pointing tests at
   `journal\runs\test-<script>\`, and T12's existing discipline — *"T12 deletes all six of its files
   and all three of its sessions"* — becomes deleting one folder.

[CONFIRMED FROM CODE] Nested creation is already relied upon: `CSSRShotBook::Shoot` calls
`FolderCreate(RunFolder())` (`:161`) on a three-level path with no parent creation anywhere, and has
done since the class shipped. [POTENTIAL_RISK] this depends on `FolderCreate` creating intermediate
directories, which no test in the tree asserts and the author has never observed on a terminal. The
new layout adds one level. **Add a single QA assertion for it** rather than a guard on every write.

`SSR_CLASS_DIR` (`SSReplay\class`, `SSR_ClassReport.mqh:33`) is **unchanged and stays a sibling**: a
class hand-in is a *copy* of `trades.csv` into `class\<student>.csv`, which is exactly what
`CSSRClassReport::Scan` globs for (`:296`). Keeping the two trees separate is what stops a coach's
scan from ingesting a student's own runs folder.

### S.5 The versioned CSV schema

#### S.5.1 The four laws

[RECOMMENDATION] Written into `SSR_Journal.mqh`'s header comment, where the honesty-column rule
already is (`:5-10`):

1. **`# SS Replay journal` stays the first line, forever.** [CONFIRMED FROM CODE]
   `CSSRClassReport::ReadOne` sets `header_seen` on exactly that prefix (`SSR_ClassReport.mqh:203`)
   and refuses the file without it (`:273-277`). It is the format's magic number.
2. **`# schema,N` is the second line.** Absent ⇒ v1. A reader that does not recognise `N` reads what
   it can and says so; it does not refuse.
3. **Columns are addressed by name, appended at the end, and never renamed, reordered or
   repurposed.** [CONFIRMED FROM CODE] the class report already resolves by name (`:238-245`), and
   the session file already states this law for its own record
   (`SSR_TradingEngine.mqh:1070-1075`). This is the product's existing rule, applied to its other
   serialised format.
4. **Undefined is empty (S.3.4). A value that is zero means zero.**

### S.6 `review.csv` — the per-trade review, written later

#### S.6.1 Why it is a second file

[CONFIRMED FROM CODE] `ExportCsv` opens with `FILE_WRITE` (`SSR_Journal.mqh:173`), which truncates.
That is the same shape as `ui-port-session-2` (CONFIRMED, **MEDIUM**) — *"the moment `Create()`
succeeds the previous save no longer exists"* — and it is exactly what must not happen to a file the
user has been adding notes to for an hour. Re-exporting `trades.csv` to attach a note would put an
hour of review behind a truncating write.

[RECOMMENDATION] So: **`trades.csv` is written once and is immutable. `review.csv` is append-only
and is joined on `ticket`.** The statement joins them at render time; the CSV consumer joins them in
the spreadsheet; neither file can damage the other.

```
# SS Replay review
# schema,1
# run_id,20260913-094107
ticket,reviewed_at,rating,mistakes,text
12,2026.09.13 21:40:02,-1,EARLY+SIZE,took it before the retest and doubled the size
```

* `rating` — `-2..+2`, the five buttons of S.8.3. Empty is *not reviewed*; `0` is *reviewed, and it
  was fine*. The S.3.4 law again, and here it is the difference between a coach seeing "twelve
  trades unreviewed" and "twelve trades rated zero".
* `mistakes` — the **user's** flags, `+`-joined, deliberately a different vocabulary from column 31's
  machine flags. The machine says `NOSTOP` because it can prove it; the trainee says `EARLY` because
  only they know. Mixing them into one column would let the file assert a judgement it cannot
  support.
* `text` — free, RFC-4180 quoted (S.10).

**Append, never rewrite:** `FileOpen(path, FILE_READ|FILE_WRITE|FILE_TXT|FILE_SHARE_READ)` then
`FileSeek(h, 0, SEEK_END)`. Re-reviewing a trade appends a **second row**; the reader takes the last
row per ticket. An append cannot lose the rows before it, which a rewrite can.

#### S.6.2 The in-memory half

[CONFIRMED FROM CODE] `p.note` already round-trips through the session file at field 27
(`SSR_TradingEngine.mqh:1097`, `:1210`) and already exports at CSV column 18
(`SSR_Journal.mqh:89`). It needs one verb:

```
   CSSRTradingEngine::SetNote(const long ticket, const string text)   // new, ~8 lines
   CSSRReplayPort::ReviewTrade(const long ticket, const string text,
                               const int rating, const string mistakes)  // new port verb
```

[RECOMMENDATION] The port verb does two things and in this order: writes the note onto the position
(so it survives a session save and reappears on resume, for free, through machinery that already
exists), then appends the row to `review.csv` (so it survives the terminal). Neither half is
sufficient alone: the session file is lost if the user never saves a session, and `review.csv` is
not reloaded into a resumed run.

[CONFIRMED FROM CODE] The port is where this belongs, not the panel: `CSSRGroupPort::SetTradeTag`
(`SSR_GroupPort.mqh:799-812`) is the existing precedent for a typed string arriving from the panel,
including its comma-stripping — *"the statement is a CSV as well as an HTML page, and a comma in a
tag would move every column after it by one"*. Under S.10's quoting that strip is no longer needed,
but the ownership is.

### S.9 The indexed accessor, and the three findings it repairs for free

#### S.9.1 The accessor

N.9's stated prerequisite, specified:

```
   struct SSRJournalRow                       // flat; two strings, no legs
     { long ticket; int slot; long open_msc; long close_msc; double net; ... };

   bool CSSRJournal::BuildIndex(void);        // one pass, O(Total()), sorted by close_msc
   int  CSSRJournal::Count(void);             // unchanged
   bool CSSRJournal::At(const int i, SSRJournalRow &out);   // O(1)
   int  CSSRJournal::IndexOfTicket(const long ticket);      // O(log n)
```

`Line(index, digits)` (`:141-157`) is deleted with it.

**When the index is rebuilt.** [CONFIRMED FROM CODE — correction to M.4.3] M states that
`m_acct.ClosedCount()` is O(1). It is not: `SSR_TradingEngine.mqh:988-994` is a loop over `m_count`
comparing a state byte. It is nevertheless the right detector, because it makes **no struct copy**,
while `At(i, p)` copies ~660 B per slot. At `SSR_MAX_POSITIONS 512` the detector is ~512 byte
comparisons and the rebuild is ~340 KB of copying. [RECOMMENDATION] poll the detector, rebuild on
change — which is the same detector and the same throttle M.4.3 gives the cached `SSRStatistics`,
and the two should share one call so the walk happens once:

```
   if(m_acct.ClosedCount() != m_closed_seen || now - m_built > 2000)
     { BuildIndex(); m_stats.Compute(m_cache); m_closed_seen = ...; }
```

[RECOMMENDATION] and make `ClosedCount()` genuinely O(1) later by maintaining a counter the way
`m_ambiguous_count` already is (`:996`) — a small change, and it must handle the rewind path that
un-closes a position, which is why it is *later* and not now.

#### S.9.2 The three findings the sort repairs

The index is **sorted by `close_msc`**, and that single property is the fix for three CONFIRMED
findings that are all one defect: *closed trades are walked in slot order, which is open order.*

| Finding | What slot order does | What the close-ordered index gives |
|---|---|---|
| `trading-analytics-3` (CONFIRMED, **MEDIUM**) — closed drawdown walks in open order (`SSR_Statistics.mqh:696-716`) | three overlapping trades A(−100, first opened, last closed), B(+1000), C(−500): the real path has a 600 drawdown, the loop reports 500 | `ClosedDrawdownFor` iterates the index instead of `At(i)`; the balance path is the one that happened |
| `trading-analytics-7` (CONFIRMED, LOW) — revenge compares with the previously **opened** trade (`:497-512`) | a textbook revenge entry one minute after a loss is missed because an unrelated winner opened in between | `prev_close`/`prev_was_loss` walk close order, which is what the printed definition (`:1196-1198`) actually says |
| `trading-analytics-3`'s tail — `win_streak`/`loss_streak` from the same loop | a streak is reported in the order trades were placed | streaks in the order they resolved, which is the order a trainee experienced them |

[RECOMMENDATION] One index, built once per change, consumed by `ComputeFor`, `ClosedDrawdownFor`,
`Bucket`, the journal's exports and the destination. **This is the best-value change in the section**
and it is a consequence of building the accessor, not an addition to it.

[POTENTIAL_RISK] `ComputeFor` currently visits slots; re-pointing it at the index changes
`win_streak`, `loss_streak`, `revenge_trades` and `max_drawdown_closed` for any session with
overlapping trades. Numbers a user has already seen will move. That is a correction, not a
regression, and it belongs in the release note beside the statement's own caveat.

#### S.10.1 Quoting — `trading-analytics-14` (**POTENTIAL_RISK, LOW**)

**Classification first, because the fix below is prescribed and the heading is not a verdict.**
`trading-analytics-14` is **POTENTIAL_RISK**, final severity **LOW**: the *code path* is confirmed
from source, but whether any real session name or tag ever contains a `"` — and therefore whether the
merge ever happens — is a user-behaviour question source cannot settle. Everything tagged
[CONFIRMED FROM CODE] below is confirmed about the code, not about the consequence being reached.

[CONFIRMED FROM CODE] `Csv()` (`:51-58`) replaces `,` with `;` and newlines with spaces, and handles
no quote. A tag or session name containing `"` is written verbatim; an RFC-4180 reader consumes
delimiters and line breaks until the next quote, merging rows.

[RECOMMENDATION] Replace with real quoting, which is strictly simpler than the current substitution:

```
   //--- RFC 4180. A field that contains a comma, a quote or a newline
   //--- is wrapped in quotes and its own quotes are doubled. Replacing
   //--- the comma instead - which this did - silently edited the user's
   //--- own words, and did nothing at all about the quote.
   string CsvField(const string s);
```

This also retires two workarounds: `CSSRGroupPort::SetTradeTag`'s comma strip
(`SSR_GroupPort.mqh:806-809`) and the `,`→`;` substitution that currently rewrites a session name.
**Note the sequencing cost**: [CONFIRMED FROM CODE] `CSSRClassReport::ReadOne` splits on commas with
no quote awareness and rejoins free-text fields with `,` (`SSR_ClassReport.mqh:212-215`). Quoting the
journal without teaching the class report to unquote **breaks the class report on the first quoted
field**. The two changes are one change.

#### S.10.2 Encoding — `trading-analytics-13` (**POTENTIAL_RISK, LOW**), and its confirmed sibling

**Classification first.** `trading-analytics-13` is **POTENTIAL_RISK**, final severity **LOW** — the
mismatch between the file mode and the declared charset is confirmed from source, but what a terminal
actually writes for a non-ASCII name under `FILE_ANSI` is a runtime question nobody here has measured
(D's coverage statement lists "no compile on MetaEditor" among the four kinds of evidence this audit
does not have). Its sibling `strategy-integration-report-8` **is** CONFIRMED, MEDIUM, which is why the
family is worth one fix.

[CONFIRMED FROM CODE] Both exports open `FILE_TXT|FILE_ANSI` (`:173`, `:254`) while
`SSRWriteReportHead` declares `charset=utf-8` (`SSR_ReportStyle.mqh:21`). A Persian session name
becomes `?` or Windows-1256 bytes inside a document that says it is UTF-8.
`strategy-integration-report-8` (CONFIRMED, **MEDIUM**) is the identical defect in the class report,
so this is a two-file family with one fix.

[RECOMMENDATION] Drop `FILE_ANSI` from both exports. Write the CSV with a UTF-8 BOM — the product
already reads UTF-8 as binary with BOM handling in the string catalogue (L.8), so the convention
exists; and the BOM is what makes Excel open a UTF-8 CSV correctly, which is the tool this file is
for. Keep `FILE_SHARE_READ`, which is why a user can have the file open while the session runs.

[POTENTIAL_RISK] Whether MetaTrader's `FILE_TXT` without `FILE_ANSI` emits UTF-16 rather than UTF-8
is a terminal question this audit cannot settle. **Write the CSV with `FILE_BIN` and explicit
`StringToCharArray(..., CP_UTF8)`** and the question does not arise — at the cost of writing the
CRLFs by hand, which the exporter already does explicitly at every `FileWriteString`.

#### S.10.3 Length

[CONFIRMED FROM CODE] The 63-character draw limit is a *panel* constraint, not a file one — the CSV
and the HTML have no width. It binds in exactly one place in this section: the twelve pre-formatted
`jrn_*` strings on the wire (S.8.5), which are drawn. Each is `Clip()`ed at its row's budget **at the
owner**, so the panel receives a string that already fits and the R5 audit A22 sees a `Clip()` at
every draw site.

### S.14 What this refuses, and what it does not fix

**Refuses:**

* **It will not make the journal a v1 destination.** M.3.2 rejected it on four grounds; three are
  addressed here (the accessor, the record, the note's owner) and one — `ui-port-session-2`/`-3`, both
  CONFIRMED HIGH — is not this section's to close. The destination ships when they do.
* **It will not show a picture in the panel.** MQL5 has no PNG object and this product has no DLL
  import; a button that writes a page and names it is the honest control (S.8.4).
* **It will not rename or reorder a CSV column**, ever, including `profit`, whose meaning is now
  wrong-looking and whose name is load-bearing for `CSSRClassReport::ReadOne` (`:243`).
* **It will not compute a measure in the journal that the statistics engine computes.** Mistake flags
  come from the pass that already counts them; `DailyRoomAfter`'s rule (M.4.1) applies here word for
  word.
* **It will not claim a *before* picture for a market order** (S.7.1). Pending orders get one because
  the state exists; market orders do not, and a rolling pre-capture is a [FUTURE FEATURE] with its own
  disk cost.
* **It will not put the review in `trades.csv`.** A file the user edits and a file the user exports
  are not the same file, and `FILE_WRITE` truncates.

**Does not fix, and says so:**

* `ui-port-session-3` — a resumed run can journal excursions that never happened. Declared in the
  header and in the caveat; not repaired.
* `trading-analytics-9` — the equity ring discards the half that carries the peak, so a statement's
  SVG can omit the trough its own label names. The header keeps the number; the curve is still short.
* `trading-analytics-2` and `-1` (the prop evaluation is not persisted, and resuming voids it) — the
  statement prints `m_prop.StateName()`/`Report()`/`Reason()` *at export time*
  (`SSR_Journal.mqh:286-297`), so a run that was voided on resume produces a document saying so. That
  is correct behaviour on top of a defect, and the defect is elsewhere.
* `core-engine-5` — `bars_consumed` is wrong by 10-1500×. It is not in the journal and must not be
  added to it.
* **The Persian case.** [POTENTIAL_RISK] S.10.2 makes a Persian session name survive the file; it
  does nothing about the fact that `flags`, `session` and `reason` are English tokens by design
  (they are a machine vocabulary), while the detail screen's rows are drawn text and inherit Q's
  unresolved mixed-direction problem. A `flags` cell reading `! no target  ~ assumed` beside Persian
  labels is a rendering outcome no source reading can predict.
* **Nothing here has run on MT5.** `FolderCreate` on a four-level path, `ChartScreenShot` capturing
  panel objects, `FILE_BIN` + `CP_UTF8` producing a CSV that Excel opens, and whether a `Render()`
  between two timer passes has repainted — four terminal questions, four places where this section
  chose the failure mode that degrades to today's behaviour rather than to no file at all.
