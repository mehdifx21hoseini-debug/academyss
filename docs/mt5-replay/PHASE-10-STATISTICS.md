## سه راهی که آمار معاملاتی دروغ می‌گوید — و پاسخ هر کدام

### ۱. R را با ضررِ **اتفاق‌افتاده** بسنجی، نه با ریسکِ **گرفته‌شده**

اگر R را از ضرر واقعی حساب کنی، **هر ضرری دقیقاً 1R- می‌شود** و معامله‌گری که هیچ‌وقت حد ضرر نگذاشته، در گزارش، انضباط کامل نشان می‌دهد.

پس `risk_at_entry` **در لحظه‌ی ورود** ثبت می‌شود:

```
if(m_pos[i].sl > 0.0)
   m_pos[i].risk_at_entry = m_risk.RiskOf(volume, |open_price - sl|);
```

تست `T10.2` معامله‌ای دارد که ۱۵۰ ریسک کرد و ۱۰۰ باخت. اگر R از ضرر محاسبه می‌شد، 1.000- می‌شد. هست: **0.667-**.

### ۲. R را برای معامله‌ی بدون حد ضرر، **صفر** اختراع کنی

R بدون حد ضرر **تعریف‌نشده** است، نه صفر.

```
bool HasR(void) { return (risk_at_entry > 0.0); }
```

- در آمار: `r_trades` می‌گوید میانگین از **چند** معامله آمده — بقیه حذف می‌شوند، نه صفر می‌شوند.
- در Caveat: `"R covers 1 of 2 trades - the rest had no stop."`
- در CSV: ستون `r` **خالی** نوشته می‌شود، هرگز `0.000`:

```
(p.HasR() ? DoubleToString(p.RMultiple(), 3) : ""),
```

چون `0.000` را هر چیزی که بعداً این فایل را باز کند، در میانگین دیگران وارد می‌کند.

تست `T10.4`: یک برنده‌ی ۱۰۰۰ واحدی بدون حد ضرر + یک برنده‌ی ۱۰۰ واحدی با ریسک ۱۰۰. میانگین R اگر بر ۲ تقسیم می‌شد ۰.۵ بود، اگر ۱۰R حساب می‌شد ۵.۵. **۱.۰ است** — روی همان یک معامله‌ای که R دارد.

### ۳. نتیجه‌ای که بر ترتیب حدسی تیک استوار است را «مشاهده‌شده» گزارش کنی

ادامه‌ی R11 از Phase 9، حالا در لایه‌ی آمار:

| جا | چه می‌گوید |
|---|---|
| `SSRStatistics.ambiguous_pct` | درصد |
| `IsTrustworthy()` | سخت‌گیرانه: بیش از ۱۰٪ → **خیر** |
| `Caveat()` | جمله‌ای که باید همراه عدد برود |
| ستون `resolution` در CSV | `ASSUMED` یا `observed` — **در هر ردیف** |
| `# CAVEAT` در Header فایل | تا فایلی که سه هفته بعد باز می‌شود هم بگوید اعدادش بر چه استوارند |

آستانه‌ی ۱۰٪ عمدی و سخت‌گیرانه است: هر چیزی بیش از یک‌دهم نتایج که بر ترتیب فرضی استوار باشد، برای عوض کردن یک نتیجه‌گیری کافی است.

## Drawdown: آنچه معامله‌گر **تحمل کرد**، نه فقط آنچه ثبت شد

دو عدد، جدا از هم:

| متریک | از کجا |
|---|---|
| `max_drawdown_closed` | فقط منحنی Balance — معاملات بسته‌شده |
| `max_drawdown` | منحنی **Equity**، نمونه‌گیری‌شده هر دقیقه‌ی Replay |

معامله‌ای که ۱۳۰ واحد به ضرر رفت و بعد با ۱۰۰ واحد ضرر بسته شد، **۱۳۰ واحد Drawdown بود که معامله‌گر رویش نشست**. گزارش کردن فقط ۱۰۰، کمتر از واقعیت است.

فاصله‌ی بزرگ بین این دو عدد یعنی معامله‌گر ضررها را **سوار می‌شده**، نه اینکه می‌گرفته.

تست `T10.2` هر دو را دقیق می‌سنجد: `closed = 100`، `equity = 130`.

## Ring نمونه‌های Equity — چرا نصف را دور می‌ریزد نه همه را

```
int keep = SSR_EQUITY_SAMPLES / 2;   // نه صفر
```

اگر کل منحنی پاک می‌شد، هر نمونه‌ی اولیه — از جمله **قله‌ای که هنوز Drawdown را نسبت به آن می‌سنجیم** — از بین می‌رفت و Drawdown ناگهان صفر می‌شد.

و `OnRewind` منحنی را **کوتاه** می‌کند: منحنی، آینده‌ای را توصیف می‌کرد که حذف شده است.

## T32 و T33 — بسته شدند

### Margin و Stop Out

بک‌تستی که هرگز Margin کم نمی‌آورد، **به هر پوزیشن بیش از اندازه‌ای که تا به حال گرفته‌ای تملق می‌گوید**.

```
CheckStopout()  →  بدترین ضررده اول، همان‌طور که بروکر می‌بندد
```

و اگر Margin مدل نشده باشد، `margin_modelled = false` و Caveat **می‌گوید** — عدد قابل‌قبولی جعل نمی‌شود.

### Swap — بازمحاسبه، نه انباشت

Swap بر تقویم **Replay** حساب می‌شود: جلسه‌ای که یک هفته را در یک عصر Replay می‌کند باید یک هفته Swap بدهد، نه یک شب.

پیاده‌سازی اول (انباشتی، با `m_last_swap_day`) دو باگ داشت که در Code Review همین Phase پیدا شد. حالا `AccrueSwap()` هر بار **بازگویی** می‌کند:

```
owed = swap_locked + per_lot * volume * (today - swap_from_day);
if(owed != p.swap) { m_balance += owed - p.swap;  p.swap = owed; }
```

سه خاصیت که از این شکل می‌آید:
1. **Idempotent** — می‌شود روی هر تیک صدایش زد.
2. **Rewind-safe** — Replay دوباره‌ی همان روزها دو بار شارژ نمی‌کند؛ Rewind از آن روزها، پول را برمی‌گرداند.
3. **درست هنگام خروج جزئی** — روزهایی که با حجم بزرگ‌تر نگه داشته شده، در `swap_locked` قفل می‌شوند و بازنویسی نمی‌شوند.

## Code Review داخلی — چهار باگ واقعی، همه در Phase 9

این Phase چهار نقص در کدِ Phase 9 پیدا کرد. هر چهار مورد از یک خانواده‌اند: **مسیر Rewind**.

### 🔴 Critical — Swap دو بار پرداخت می‌شد

`ChargeSwap()` مبلغ را به `m_balance` اضافه می‌کرد، و بعد `ClosePosition` دوباره `+ m_pos[i].swap` می‌کرد.

```
- m_balance += realised - fee + m_pos[i].swap;
+ m_balance += realised - fee;      // Swap قبلاً هنگام تعلق اعمال شده
```

تست `T10.5` این را پین می‌کند: بستن پوزیشن، Balance را جز به اندازه‌ی نتیجه‌ی قیمتی تکان نمی‌دهد.

### 🔴 Critical — خروج جزئی از Rewind جان سالم به در می‌برد

**ساکت‌ترین باگ این مجموعه.** `OnRewind` فقط پوزیشن‌های `CLOSED` را بازمی‌گرداند و حجم را به `volume_initial` برمی‌گرداند. پس اگر معامله‌گر نصف پوزیشن را برداشته بود و بعد Rewind می‌کرد:

- خروج جزئی **باقی می‌ماند**، سودش **در Balance ثبت‌شده** می‌ماند،
- و معامله‌گر با حجمی برمی‌گشت که **هنوز تصمیم به گرفتنش نگرفته بود**.

این دقیقاً همان کلاس باگی است که Phase 9 برای جلوگیری از آن نوشته شد و خودش مرتکبش شد.

**راه‌حل: دفتر Leg.** هر کاهش حجم — جزئی یا نهایی — یک `SSRTradeLeg` است:

```
struct SSRTradeLeg
  {
   double volume, price, realised, fee;
   long   msc;
   bool   closing;
   double prev_swap_locked;    // آنچه این Leg بازنویسی کرد
   long   prev_swap_from_msc;
   bool   prev_ambiguous;
  };
```

- **یک** مسیر برای خروج: `BookExit()`
- **یک** چیز برای Rewind که باز کند: `UnwindLegsAfter()` — از تازه‌ترین به قدیمی‌ترین

کد قبلی `volume_initial` و کمیسیون را دستی جابه‌جا می‌کرد؛ آن حساب‌داری حالا حذف شده است.

### 🟠 High — سفارش Pending که در آینده‌ی حذف‌شده پر شده بود

Pending هنگام پر شدن، `type` و `open_msc` خودش را بازنویسی می‌کند. پس Rewind:
- یا آن را **کاملاً حذف** می‌کرد (چون `open_msc > msc`)،
- یا **پرشده** رهایش می‌کرد، با قیمتی که Replay همین حالا آن را نکرده اعلام کرده بود.

حالا `request_msc` و `request_type` نگه داشته می‌شوند و سفارش **به همان شکلی که ثبت شده بود** به تخته برمی‌گردد. لغو Pending هم زمان‌دار شد تا Rewind بتواند بازش گرداند.

### 🟡 Medium — کمیسیون سوم

`OnRewind` کمیسیونِ بستن را به Balance برمی‌گرداند ولی از `p.commission` کم نمی‌کرد. بستنِ دوباره، **سه سمت** برای یک معامله‌ی دو سمته شارژ می‌کرد. تست `T10.5c`.

## اتصال به Host

مدل اجرا **همه‌اش Input است**، نه ثابتِ دفن‌شده در کد — چون هر کدام یک **فرض** درباره‌ی یک بروکر است:

```
InpBalance · InpCommission · InpSlippage · InpSwapLong · InpSwapShort
InpMarginLot · InpStopout
```

هر کدام صفر بماند یعنی آن هزینه **مدل نشده** — و آمار این را با صدای بلند می‌گوید.

ترتیب ثبت ناظرها اهمیت دارد:

```
AddObserver(g_acct);    // اول: حساب، تیک را می‌بیند
AddObserver(g_stats);   // بعد: آمار، Equity حاصل از آن را نمونه می‌گیرد
```

و در خروج، نتایج **با جلسه نمی‌میرند**: خلاصه به Log، جزئیات به CSV، هر دو حامل Caveat.

## نکته‌ی Compile برای Phase 16

`SSRVirtualPosition` حالا یک آرایه‌ی ثابت از `SSRTradeLeg` را در خود دارد و در `OnRewind` با انتساب Struct جابه‌جا می‌شود (`m_pos[keep] = m_pos[i]`). MQL5 انتساب Struct را عضو-به-عضو انجام می‌دهد و آرایه‌های ثابت داخلی را کپی می‌کند — اما این اولین جایی در این پروژه است که به آن تکیه می‌کنیم، پس **در QA اولین چیزی است که باید تأیید شود**. اگر کامپایلر مخالفت کرد، Plan B: دفتر Leg به یک آرایه‌ی موازی در خود Engine منتقل می‌شود و در فشرده‌سازی `OnRewind` همراه پوزیشن جابه‌جا می‌شود.

هزینه‌ی حافظه: ۵۱۲ پوزیشن × ۸ Leg ≈ ۲۳۰ کیلوبایت ثابت.
