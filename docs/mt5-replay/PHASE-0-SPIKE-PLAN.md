**هدف:** PROVE THE ARCHITECTURE BEFORE BUILDING THE PRODUCT
**قاعده:** هیچ Feature محصولی، UI نهایی، Trading Simulator یا Statistics Engine ساخته نمی‌شود.
**خروجی:** اعداد واقعی اندازه‌گیری‌شده + تصمیم PASS/FAIL برای هر فرض معماری.

## اصول اندازه‌گیری

### قاعده «هیچ قضاوت کیفی»

ممنوع: «خوب بود» · «کند بود» · «روان کار کرد»
الزامی: عدد، واحد، شرایط اندازه‌گیری.

هر تست خودش اعداد را در فایل CSV می‌نویسد. قضاوت انسانی فقط روی PASS/FAIL نهایی است،

### دو متریک که MQL5 مستقیماً نمی‌دهد — و راه‌حلشان

**۱. CPU درصد.** MQL5 هیچ API برای مصرف CPU ندارد. `TERMINAL_CPU_CORES` فقط تعداد
هسته را می‌دهد. پس CPU به‌صورت **دستی** از Task Manager در چک‌پوینت‌های مشخص ثبت می‌شود.

**۲. روان بودن ترمینال.** به‌جای CPU که معیار غیرمستقیمی است، معیار بهتری داریم:
**UI Jitter**. یک Indicator با `EventSetMillisecondTimer(50)` روی چارت جداگانه
اجرا می‌شود و اختلاف بین زمان مورد انتظار و زمان واقعی فراخوانی `OnTimer` را ثبت می‌کند.

> اگر Timer که باید هر ۵۰ms صدا زده شود با ۴۰۰ms تأخیر صدا زده شود، یعنی
> Thread ترمینال گرسنه است — دقیقاً همان چیزی که کاربر به‌عنوان «Freeze» حس می‌کند.

این متریک از CPU% دقیق‌تر است، چون همان چیزی را می‌سنجد که واقعاً اهمیت دارد.
Probe: `SSR_Probe_UIJitter.mq5`

معیار اولویت: **«اگر این تست FAIL شود، چقدر از معماری باید عوض شود؟»**

| Tier | تعداد | اگر FAIL شود | باید قبل از ادامه اجرا شود |
|---|---|---|---|
| **A — Foundation Gates** | ۳ | کل پروژه از پایه بازطراحی می‌شود | بله — Gate |
| **B — Transport Layer** | ۴ | لایه انتقال از Tick به Bar تغییر می‌کند | بله |
| **C — Process Model** | ۴ | Service → EA با State Persistence | بله |
| **D — Performance Envelope** | ۴ | محدوده محصول کوچک‌تر می‌شود، معماری نه | خیر — می‌تواند موازی |

**ترتیب اجرا:** `A1 → A2 → A3 → B1 → B2 → B3 → B4 → C1 → C2 → C3 → C4 → D1 → D2 → D3 → D4`

اگر هر تست Tier A شکست بخورد، **متوقف شو و برگرد به Architecture Review.**
