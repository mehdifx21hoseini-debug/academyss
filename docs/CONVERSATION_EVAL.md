# ارزیابی مکالمه (`conversation-eval-*`)

**وضعیت:** ابزار ساخته شده · هنوز روی داده‌ی واقعی اجرا نشده · ADR-052

سؤال: **اگر فقط لحن و راهنمای رفتاری عوض شود، منتور پاسخ را بهتر می‌بیند؟** ابزار دو نسخه را
روی همان پیام‌ها، با همان زمینه و همان دروازه‌ها، کور مقایسه می‌کند.

| بازو | چیست |
|---|---|
| **A** | رفتار فعلی: `SYSTEM_PROMPT` + چهار پیام قبلی + حافظه‌ی دانشجو + بازیابی + `silence_reason_for` |
| **C** | همان ورودی و همان دروازه؛ فقط بندهای لحن (۷ تا ۹) و یک پیوست نمونه عوض می‌شود |

بازوی B (زنجیره‌ی E2E) عمداً در این نسخه نیست. نویسنده‌ی E2E تاریخچه و حافظه را نمی‌بیند، پس
مقایسه‌ی «پیوستگی» با A منصفانه نیست. اگر روزی اضافه شود، آن محدودیت باید کنار نتیجه بیاید.

## سه فرمان

```bash
# ۱) آماده‌سازی. بدون مدل. فقط‌خواندنی. با --check فقط شمارش (هیچ فایلی نوشته نمی‌شود).
docker compose run --rm cli mentorai conversation-eval-prepare --limit 30 --seed 7 --check
docker compose run --rm cli mentorai conversation-eval-prepare --limit 30 --seed 7 \
    --variant /out/tone_variant.json --out /out/conv_eval1

# ۲) اجرا. مدل صدا زده می‌شود (هزینه دارد). به پایگاه داده وصل نمی‌شود.
#    بدون --approve فقط خلاصه و بدترین هزینه چاپ می‌شود و خارج می‌شود (کد ۲).
docker compose run --rm cli mentorai conversation-eval-run \
    --prepared /out/conv_eval1/prepared.json --arms A,C --max-cost-usd 3 --approve <کد>

# ۳) گزارش پس از داوری. بدون مدل.
docker compose run --rm cli mentorai conversation-eval-report \
    --key /out/conv_eval1/key.json --graded /out/conv_eval1/blind_sheet.csv
```

## ایمنی (و چگونه آزموده شده)

- `prepare` فقط روی نشستی اجرا می‌شود که **اتصالش** `default_transaction_read_only=on` دارد؛
  نشست نوشتنی را رد می‌کند. `SET TRANSACTION READ ONLY` به‌تنهایی کافی نیست، چون با هر commit
  تراکنش بعدی دوباره نوشتنی می‌شود.
- `run` هیچ اتصال پایگاه داده‌ای ندارد؛ همه‌چیز از `prepared.json` می‌آید.
- ماژول import از تلگرام، تحویل، پیش‌نویس، ارجاع، کارگر، `handle_message` و هر نشست نوشتنی
  ندارد، و هیچ فراخوانی `add/commit/flush/delete/…` ندارد (آزمون AST).
- آزمون‌ها شمارش ردیف همه‌ی جدول‌ها را پیش و پس از اجرا می‌سنجند.
- مدل فقط با `--approve <کد ۸ نویسه>` ساخته می‌شود. کد از هش محتوای کامل `prepared.json` است؛
  فایل دستکاری‌شده رد می‌شود.
- متن خطای ارائه‌دهنده ذخیره نمی‌شود (فقط نوع خطا)، چون ممکن است کلید را بازتاب دهد.

## سقف هزینه

پیش از هر نمونه (جفت فراخوانی) بدترین هزینه‌ی ممکن محاسبه می‌شود: ورودی ≤ یک توکن به ازای هر
نویسه، ضریب نوشتن حافظه‌ی نهان ۱٫۲۵، و خروجی تا `AI_MAX_TOKENS`. در حالت **`strict`** (پیش‌فرض)
نمونه‌ای شروع نمی‌شود که `خرج تا اینجا + بدترین حالت آن` از سقف بگذرد.

**محدودیت‌های صریح:**

1. «یک توکن به ازای هر نویسه» فرض است، نه قانون. اگر فراخوانی توکن بیشتری گزارش کند، اجرا
   می‌ایستد (`estimate_violated`).
2. `usage.input_tokens` نوشتن حافظه‌ی نهان را نمی‌شمارد (کلاینت فعلی `cache_creation` را ثبت
   نمی‌کند). ابزار برای هر فراخوانی بدترین حالتش را اضافه می‌کند، پس «هزینه‌ی محاسبه‌شده» کمی
   بیش از «اندازه‌گیری‌شده» است. مسیر زنده همان کم‌شماری را دارد.
3. تلاش دوباره‌ی خودکار SDK تا سه بار صدا می‌زند. ابزار آن را خاموش می‌کند (`max_retries=0`)؛
   اگر نشد، بدترین حالت ×۳ حساب می‌شود و در خلاصه گفته می‌شود.
4. بدترین حالت با `AI_MAX_TOKENS=8000` گران است (حدود ۰٫۰۹ دلار برای هر فراخوانی با Sonnet 5.5).
   `prepare` می‌گوید حتی در بدترین حالت دست‌کم چند نمونه کامل می‌شود؛ معمولاً بیشتر اجرا می‌شود،
   چون هزینه‌ی واقعی بسیار کمتر است. `--max-output-tokens` فقط برآورد را عوض می‌کند، نه
   فراخوانی را.
5. حالت `measured` به‌جای بدترین حالت از ۱٫۵ برابر گران‌ترین نمونه‌ی دیده‌شده استفاده می‌کند و
   **ممکن است حداکثر یک نمونه از سقف بگذرد.** فقط با درخواست صریح.
6. هزینه در `model_usage` ثبت نمی‌شود و از سقف روزانه‌ی `AI_DAILY_BUDGET_USD` کم نمی‌شود.
   سقف بیرونی در کنسول Anthropic تنها محافظ مستقل از کد است.

## ناشناس‌سازی

ایمیل، نام کاربری تلگرام و رشته‌های ۹ رقمی و بیشتر (`mask_personal`) در پرسش، تاریخچه و حافظه
پوشانده می‌شود. نام‌های **ذخیره‌شده‌ی** همان گفتگو (دانشجو و منتور) روی مرز واژه به `[نام]`
تبدیل می‌شود. نام در متن آزاد (مثلاً نام شخص سوم) را نمی‌شود صددرصد گرفت. شناسه‌ی نمونه در
برگه `C01…` است؛ شناسه‌ی پیام فقط در `key.json` می‌ماند. فایل‌ها ۶۰۰ و پوشه ۷۰۰ است.

## نسخه‌ی لحن (بازوی C)

فایل JSON:

```json
{
  "version": "tone-1",
  "rules": {"7": "…", "9": "…"},
  "appendix": "نمونه‌هایی از لحن (متن آزاد، بدون بند شماره‌دار)"
}
```

فقط بندهای ۷ تا ۹ و پیوست مجازند. بندهای دیگر (منبع، قیمت، وعده‌ی سود، سیگنال، داده بودن متن
دانشجو، افشا، شناسه‌ها) باید بایت‌به‌بایت برابر A بمانند، وگرنه ابزار رد می‌کند. متن نباید
تلفن، ایمیل یا نام کاربری داشته باشد. **متن نسخه‌ی لحن پیش از اجرا باید مالک تأیید کند.**

## محدودیت‌های مقایسه

- حافظه‌ی دانشجو وضعیت **امروز** است، نه لحظه‌ی پیام. تاریخچه با `id` کمتر از پیام است.
- فقط پیام متنی. شرط `assistant_may_answer` و `budget.check` اجرا نمی‌شوند.
- مدل غیرقطعی است؛ یک اجرا یک نمونه از رفتار است.
- کور بودن کامل نیست: سبک نوشتار لو می‌دهد. ارزیاب دوم توصیه می‌شود.
- ۳۰ نمونه نتیجه‌ی قطعی نمی‌دهد؛ گزارش خودش این را می‌گوید.
- آزمون‌ها ایمنی و درستی ابزار را می‌سنجند، نه کیفیت فارسی را.

## معیارهای داوری

نُه معیار جدا (۱ تا ۵): صحت آموزشی، درک منظور، پیوستگی با تاریخچه، طبیعی بودن لحن، تناسب
طول، سؤال روشن‌کننده، تکرار و کلیشه، ارجاع مناسب، رعایت سیاست آکادمی؛ به‌علاوه «کلی» (۰ تا ۳)
و سه پرچم (ساخته‌شده، باید ساکت می‌ماند، باید ارجاع می‌شد). تعریف هر نمره در
`grader_guide.txt` است. گزارش میانگین‌ها را به تفکیک معیار می‌دهد و موارد بحرانی را جدا فهرست
می‌کند؛ **آستانه‌ی قبولی را مالک تعیین می‌کند**، ابزار فقط می‌شمارد.
