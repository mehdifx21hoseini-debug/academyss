# لایه‌ی پرسش و پاسخ منتور

## وضعیت فعلی
هیچ داده‌ی واقعی‌ای دریافت نشده است. این پوشه ساختار و قرارداد ورودی را مشخص می‌کند
تا به‌محض دریافت داده، پردازش بدون تغییر ساختار شروع شود. (مورد `RQ-0002`)

## مسیر پردازش

```
raw_sources/mentor_qa/        فایل خام صادرشده از تلگرام/واتس‌اپ/تیکت — دست‌نخورده
        ↓ پاک‌سازی و حذف اطلاعات شخصی
knowledge_base/mentor_qa/cleaned/     گفت‌وگوی تمیز، بدون نام و شماره و اطلاعات شخصی
        ↓ استخراج دانش
knowledge_base/mentor_qa/structured/  رکورد MQA طبق schemas/mentor_qa.schema.json
        ↓ اعتبارسنجی و تطبیق با محتوای آکادمی
knowledge_base/mentor_qa/approved/    رکوردهای تأییدشده (حداکثر MENTOR_VERIFIED)
```

## قالب ورودی موردنیاز

هر قالبی که این چهار چیز را داشته باشد کافی است:

| فیلد | توضیح |
|---|---|
| متن پیام | متن کامل پرسش دانشجو |
| متن پاسخ | پاسخ منتور |
| نقش فرستنده | مشخص باشد پیام از دانشجو است یا منتور |
| زمان پیام | برای ترتیب گفت‌وگو و تشخیص نسخه‌ی قدیمی/جدید قواعد |

قالب‌های پذیرفته‌شده: `JSON` (خروجی Telegram Desktop)، `CSV`، `TXT` یا خروجی تیکت.

## قواعد ثابت

* فایل خام هرگز ویرایش نمی‌شود؛ فقط در `raw_sources/mentor_qa/` بایگانی می‌شود.
* نام، شماره تماس، آی‌دی و هر اطلاعات شناسایی‌کننده پیش از خروج از `raw_sources/` حذف می‌شود
  (`pii_removed = true`).
* پاسخ منتور هرگز `ACADEMY_PRIMARY` نمی‌شود (قاعده‌ی `MET-RULE-0004`).
* پاسخ‌های متناقض حذف نمی‌شوند؛ برایشان `CONFLICT_RECORD` ساخته می‌شود.
* سؤال‌های تکراری با `cluster_id` به هم متصل می‌شوند تا «۴۷ سؤال با یک مفهوم مشترک» یک بار پاسخ داده شود.

نمونه‌ی ساختار خروجی: `schemas/examples/mentor_qa_example.json` (نمونه‌ی ساختگی برای نمایش قالب،
عمداً بیرون از `knowledge_base/` نگه داشته شده تا وارد پایگاه دانش نشود).
